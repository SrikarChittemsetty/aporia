# Aporia — web frontend

React/TypeScript UI for the Aporia search API. Next.js 16 App Router, Tailwind v4,
built as a static export so it can be hosted anywhere.

```
frontend/
  app/page.tsx          state, URL sync, every error path
  components/           SearchBar, StanceColumn, PassageCard
  lib/api.ts            typed client for the Python backend
  lib/demo.ts           offline corpus + claim matching
  lib/search.ts         picks a source and decides what the user is told
  public/demo-data.json 12 pre-computed claims, generated by scripts/export_site.py
```

## Running it

```bash
npm install
npm run dev          # http://localhost:3000
```

That serves the **offline demo**: results come from `public/demo-data.json`, which
holds real output — retrieval through the from-scratch HNSW index, stance labels
from the same Claude prompt the live pipeline uses — recorded for 12 claims.

To run against the real backend, start the API and point the app at it:

```bash
# from the repo root
.venv/bin/uvicorn api.main:app --port 8080

# frontend/.env.local
NEXT_PUBLIC_APORIA_API=http://127.0.0.1:8080
```

Now any claim works, not just the twelve, and passages gain a *read in context*
link backed by `GET /passage/{id}`.

## Two sources, one contract

The API groups results into `for` / `against` / `nuance`, and the offline export
uses an identical passage shape, so `lib/types.ts` describes both. The only
runtime difference is what `lib/search.ts` decides to do on failure:

| Situation | Result |
|---|---|
| No `NEXT_PUBLIC_APORIA_API` | Offline corpus, labelled **offline demo** |
| Live call succeeds | Live result, labelled **live backend** |
| Backend unreachable | Offline corpus + the reason it fell back |
| Backend returns 429 | **Error shown, with a countdown** |
| Backend returns 422 | **Error shown** |

The last two rows are the point. Falling back to demo data on a rate limit would
make the quota look imaginary, and falling back on a rejected query would imply
the backend accepted something it refused. Both propagate instead. The UI never
shows a result without saying which source produced it.

## Tests

```bash
npm test
```

18 tests over the logic that decides what the user is shown. The ones worth
knowing about assert the two *negative* rules, because they are the easy things
to get wrong later:

- `does NOT swap demo data in for a rate limit`
- `does NOT swap demo data in for a rejected query`
- `reports the outage, not the corpus miss, when both fail`

Plus `findClaim` returning null rather than the nearest claim when nothing is
close — a wrong answer here is indistinguishable from a right one to the reader,
so declining is the correct behaviour.

## Deploying

`next.config.ts` sets `output: "export"`, so `npm run build` emits a static
`out/` directory with no server component. Vercel, S3 and GitHub Pages all serve
it as-is.

Set `NEXT_PUBLIC_APORIA_API` in the host's environment to attach a live backend.
It is inlined into the client bundle at build time and is readable by anyone
loading the page — only public URLs belong there. The Anthropic key stays on the
backend and never reaches this app.
